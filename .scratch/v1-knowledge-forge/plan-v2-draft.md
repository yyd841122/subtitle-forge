## 拆票原则（本计划的验收标准）

1. **Implementation-ready**：fresh agent 只读 当前票 + 当前代码 + 必要上游事实
   （Spec 条款、已完成的先行票产物），即可开工；不需要读任何后续票。
   保障机制有三：
   - 每票带「明确不含」边界 + **触界行为**（未实现的后续语义继续 fail loud
     或明确拒绝——沿用 Ticket 01 `OutOfScopeVerdictError` 的先例）；
   - 每票自含所需词汇（如「处理记录」「快照」在引入它的票内定义，后续票按
     当时的代码与产物理解，不按未来票理解）；
   - 「票内裁定」逐项对应 Spec《Open Implementation Decisions》编号，
     计划不预锁任何 How。
2. **单一产品增量**：每票增加一个可观察的产品行为，验收断言全部落在外部
   产物上（Testing Decisions：唯一测试接缝 = 端到端管线含运行请求）。
3. **单 session 可完成**：每张票按「一个 session 内可靠完成并验收」设计；
   曾预估超支的票已**实际拆分**（11a/11b、13a/13b、14a/14b、22a/22b、23a/23b/23c），
   不再依赖备注式拆分线。
4. **更小的 vertical slice 优先**：不为凑覆盖面把多个职责绑进一张票。
5. **不追求少票覆盖 A1–A22**：共 28 张票（02…23c；采纳时可顺序编号 02–29）渐进覆盖。
6. Ticket 01 不动。

## 全局约定（所有票继承）

- **测试接缝**：沿用 Ticket 01 先例——CLI 端到端驱动（`--stub-module` 注入
  替身）、从落盘产物解析 JSON 块断言、路径类断言从 `asset_organization`
  自描述清单读取。断言只对外部产物，不锁内部结构。
- **依赖图是唯一的顺序事实**：下文「推荐线性顺序」仅为串行便利；任何满足
  硬依赖图的合法拓扑（含并行）下实施，各票语义不变。票号不承担依赖语义。
- **状态/类别值域**：沿用 ADR-0006 值域约定（Source `success/failed/needs_review`；
  Unit `passed/rejected/needs_review/failed`；Gap `execution_failure/audit_rejection/coverage_concern/warning`）。
- **reader 与黑盒消费者的区分**：10 票落地的 canonical reader 是**系统内部**
  的重建/回放通道（11a/12/21 使用）；外部消费者（A8）依自描述结构用通用
  JSON 解析即可，**不依赖本系统**（22b 以黑盒测试钉死这一边界）。
- **裁定记录**：凡触及 Open Implementation Decisions 或外部产物 schema 的
  裁定 → 记 ADR（Ticket 01 / ADR-0006 先例）；其余小裁定记票内即可。
- **旧票号引用清理**：代码注释中残留的旧票号引用（pipeline.py、roles.py、
  cli.py、assets.py、artifacts.py、ass.py、model.py 中的「02/03/04/05/08/09/
  12/13/14/15 票」字样）与新编号不再对应。规则：每票触及某文件时，顺手把
  该文件注释里的旧票号引用改为 Spec/ADR 条款引用（更耐久），不集中重构。
- **措辞约定**：Spec 的 必须/不得/应该 直接按条款号引用进各票验收。

## 阶段一（02–08）：Corpus 批处理成立 + 审计门核心

单元级全部下落（通过/拒绝/待复核/无引用）与 Source 级失败隔离落齐。
这是产品可信故事的主干，也是后续一切票的语义地基。

### 02 — Corpus 批处理：多 Source 顺序完成，互不污染

- **产品增量**：一个 Corpus 目录含 ≥2 个合法 ASS Source，一次 `run` 全部
  顺序处理完成；每个 Source 各自产出忠实层资产，可信发布集与运行摘要
  覆盖全部 Source 且归属正确；任何 Source 的知识单元不会出现在另一
  Source 的产物中。
- **Spec 锚点**：R1.1（Corpus 为批处理单位）、R6.4（资产与 Source 明确
  对应）、A3（单次运行内全量对账的部分）。
- **验收（外部产物断言）**：
  - 两个 Source，**一个 stub module**（`StubExtractor.script` 同时含 ep01、
    ep02 各自的独立脚本条目）→ 退出码 0；`asset_organization` 清单中
    两个 Source 的忠实层资产各就各位；
  - 每份忠实层资产的 unit_id 集合与该 Source 的脚本精确一致；trusted-set
    按 `source_id` 分组后的集合分别与两份脚本一致，条目总数 = 两组之和；
  - run-summary 两个 Source 均 `success`，各自单元状态齐全；gap-report 为空。
- **当前代码锚点**：`cli.py` 多 Source 拒绝守卫（现 64–73 行）；
  `assets.write_all` 单 Source 签名（现 233 行起）；`pipeline.run_corpus`
  已按 Source 循环（预计不改）。
- **明确不含（触界行为）**：Source 失败隔离——任一 Source 异常仍使整次
  运行失败（fail loud，07 票落隔离）；运行范围控制——仍只有全量一种请求
  形态（09 票）；跳过/幂等——每次全量重处理（10/11a 票）；空 Corpus 仍
  明确拒绝（维持现状，不在本票改变）。
- **票内裁定**：批处理顺序语义（现状为文件名序、确定性，确认即可）；
  触及文件注释的旧票号清理。
- **依赖**：无（Ticket 01 之后即可开始）。

### 03 — 审计拒绝的下落（单元级拒绝成立）

- **产品增量**：推理审计结论为「拒绝」的知识单元不进可信发布集；缺口
  报告出现 `audit_rejection` 条目（含 Source、指向单元、原因、下落）；
  运行摘要该单元 `rejected`；**含被拒单元的 Source 仍为 `success`**
  （全部单元有明确下落即成功，A4 语义）。
- **Spec 锚点**：R3.5、R4.2、A2、A4、A11（audit_rejection 部分）。
- **验收**：fixture 按 **A2 场景**构造——单元带**真实存在于原文的引用** +
  **明显越界的陈述**（如引用只讲基准情形、断言却推广到全部递归），推理
  审查替身因此对该 unit_id 预设 `reject` + 理由 → 发布集无该单元；
  gap-report 含 `{category: audit_rejection, source_id, subject: unit_id,
  reason, outcome}`；run-summary 该单元 `rejected`；Source `success`；
  同 Source 其余单元不受影响。
- **当前代码锚点**：`pipeline.py` 94–97 行（`verdict != "pass"` 的
  `OutOfScopeVerdictError` 分支）；`StubInferenceAuditor` 已支持按 unit
  预设结论。
- **明确不含（触界行为）**：忠实性程序比对（假引用场景，04 票——本票
  替身拒绝是唯一拒绝来源）；待复核（05 票，`inconclusive` 分支继续
  fail loud）；无引用单元（06 票，`missing_source_reference` 挡板保留）。
- **票内裁定**：拒绝条目 `outcome` 字段的可观察措辞（如「不进入发布集，
  记录在案」）。
- **依赖**：无硬依赖（与 02 可并行；建议 02 后在批处理语境下验收）。

### 04 — 忠实性审计的程序比对（假引用拦截）

- **产品增量**：即使推理审计替身判「通过」，凡 `quoted_text` 无法在所指
  Source 的原文中程序比对成立的单元，一律不进可信发布集，并以
  `audit_rejection` 落缺口报告。审计门自此 = **程序比对 ∧ 推理审计**
  双通过。
- **Spec 锚点**：R3.1、A1、Implementation Decisions 2/5（忠实性审计含
  纯程序比对部分，不经由生成同一内容的替身自评）。
- **验收**：替身产出「引用文本不存在于原文」的单元 + 审查替身 `pass` →
  该单元不在发布集；gap-report 的 `audit_rejection` 条目可辨原因来自
  忠实性比对；同 run 中真引用单元照常通过（比对不误伤）。
- **当前代码锚点**：`pipeline.py` 单元准入段（`_trusted_entry` 之前）；
  `Segment.text` 为比对基准（`ass.py` 保留解析后原文形态）。
- **明确不含**：比对容差的真实数据调优（票内先裁初始算法即可）；推理
  审计角色本身的行为（03 票）。
- **票内裁定**：Open Impl 10 初始算法（精确匹配或最小规范化后匹配）；
  该检查在管线中的位置（发布集准入前的程序门，不经任何认知角色）。
- **依赖**：03（复用拒绝下落机制）。（保留与 03 的分拆：03 是处置分支、
  04 是新程序组件，两个独立的 How 决策不绑定一张票。）

### 05 — 待复核（inconclusive）语义

- **产品增量**：推理审计结论「不确定」的单元 → `needs_review`、不进
  发布集、运行摘要记录明确理由（无法可靠判定，非低质量兜底）；该
  Source 整体 `needs_review`（存在未获最终结论的问题）。
- **Spec 锚点**：R4.4、R4.6、A14。
- **验收**：替身对某单元返回 `inconclusive` + 理由 → 发布集无该单元；
  run-summary 该单元 `needs_review` 且 reason 非空（断言理由文本来自
  替身结论，不是兜底措辞）；Source `needs_review`；其余单元不受影响。
- **当前代码锚点**：`pipeline.py` inconclusive 分支（与 03 分道：03 处理
  reject，本票处理 inconclusive）；`artifacts.py` 的 needs_review 常量已备。
- **明确不含（触界行为）**：人工复核流程/界面（V1 无）；needs_review
  单元是否进缺口报告（A14 只要求运行摘要——默认不进，若票内裁定要进
  须记录理由）。
- **票内裁定**：Source `needs_review` 的构成条件初始裁定（建议：任一
  单元 needs_review ⇒ Source needs_review，可改）。
- **依赖**：03（软依赖：同一分支结构的处置先例）。

### 06 — 无 Source Reference 单元的下落

- **产品增量**：无有效 Source Reference 的知识单元不进可信发布集，且在
  运行摘要/缺口报告有显性下落（状态取值与 Gap Category 归属由票内
  裁定——R2.4 明示属实现决策）。
- **Spec 锚点**：R2.4、A17。
- **验收**：替身产出无引用单元（其余正常）→ 该单元不在发布集；
  run-summary 有其记录（状态可辨、reason 提「无来源引用」）；
  gap-report 有指向它的条目；Source 的最终状态与 A4 语义一致
  （单元有下落即不妨碍 success——若票内裁定不同须记录理由）。
- **当前代码锚点**：`pipeline.py` 98–101 行（`source_reference is None`
  的挡板）；`model.KnowledgeUnit.source_reference` 本就可为 `None`。
- **明确不含**：引用有效性分级体系（如 segment_id 不存在等细分场景，
  票内可顺手覆盖 locator 校验但须记录，不展开体系）。
- **票内裁定**：**开工即先落**无引用单元的实体状态取值
  （rejected/failed 之一）与 Gap Category 归属，并记入票面（验收断言
  按裁定后的取值表达）。
- **依赖**：03。

### 07 — Source 失败隔离与继续批处理

- **产品增量**：某 Source 的处理抛错（替身脚本注入）→ 该 Source
  `failed`、缺口报告 `execution_failure` 条目、其余 Source 照常完成、
  运行结束可辨部分失败；全局性错误仍中止整批。
- **Spec 锚点**：R4.6（Source 失败）、R4.2、R5.5、A3（注入失败部分）、
  A11（execution_failure 部分）。
- **验收**：三 Source、第二个提炼替身抛错 → ep01/ep03 正常产出且发布集
  含其单元；ep02 `failed` + gap `execution_failure` 条目（含原因）；
  退出码非 0 且输出可辨部分失败（具体退出码票内裁定并断言）；全部
  Source 均有状态（无静默消失）。全局错误场景钉死一个具体 fixture
  （资产目录不可写）→ 明确中止，无半成品全局产物。
- **当前代码锚点**：`pipeline.run_corpus` 的 Source 循环（当前异常直接
  冒泡，无隔离）；`cli.py` 错误输出。
- **明确不含（触界行为）**：失败 Source 的重跑语义（09/11a 票——本票
  失败后重跑即全量重处理）；全局错误判定清单的完备化（票内只裁初始
  判据）。
- **票内裁定**：Open Impl 13 初始清单（Source 局部错误 vs 全局错误的
  判据）；部分失败的退出码/报告形态。
- **依赖**：02。（保留与 02 的分拆：02 先建立正常批处理形态，07 只加
  失败隔离语义。）

### 08 — 噪声容忍的确定性验收（解析级显性化 + 内容级容忍）

- **产品增量**：噪声与解析异常**不使处理失败、且显性可观察**：
  (a) 解析级——被跳过的畸形行/空文本事件以 `warning` 缺口条目显性化
  （含 Source、跳过原因、下落「不影响处理」）；(b) 内容级——含口头
  填充、重复、轻微转写错误的 Source 端到端处理不失败，噪声文本不出
  现在知识单元（替身脚本化：脚本单元只锚定知识性 Segment），正常
  知识照常提炼。这是 **A13 的确定性验收形态**。
- **Spec 锚点**：R1.3、A11（warning 类）、A13（确定性半边）、R4.2。
- **验收**：
  - 畸形 fixture 钉死两类：字段不足导致正则不匹配的行；清洗后空文本
    事件。→ Source 不失败、知识单元照常；gap-report `warning` 条目含
    source_id / reason（行号或行内容可辨）/ outcome。无效时间戳是否
    计入 warning 由票内裁定（当前 `_parse_ass_timestamp` 会抛异常——
    裁定其归属：warning 化或维持全局错误，记录理由）；
  - 噪声 fixture：Dialogue 含填充/重复/轻微错字的 Source → 处理不失败；
    断言全部知识单元的 statement 与 quoted_text 均不含噪声片段、只含
    知识性片段；正常单元照常进发布集；
  - 无畸形、无噪声的运行 warning 为空。
- **当前代码锚点**：`ass.py` 58/62 行的静默 skip（需把跳过信息传到
  运行层，承载形态票内裁定）；`conftest.py` 的受控 ASS 先例。
- **明确不含**：真实模型对噪声的**内容判断质量**——那是概率性行为，
  由 23c 以非门禁 eval 覆盖，**不计入 A13 的验收声明**。
- **票内裁定**：跳过信息的承载形态（Source 模型字段 vs 解析报告结构）；
  无效时间戳的归属。
- **依赖**：无硬依赖（`GapEntry` 结构自 Ticket 01 即存在；03 仅为缺口
  条目的实现先例，不是依赖——依赖图保持唯一顺序事实）。07 后实施更
  自然（批处理语境），非硬依赖。

## 阶段二（09–14b）：运行形态与重算语义

范围控制 → 完整快照与 reader → 跳过判定 → 变化检测 → 中断恢复 →
版本 → 步骤重跑。这条链是 ADR-0004 产品原则的落地线。

### 09 — 运行范围控制（指定 Source 子集）

- **产品增量**：运行请求可指定 Source 子集，仅处理被选 Source；未选

### 10 — 每 Source 完整结局快照与 canonical reader

> 本票引入两个后续重算链（11a/11b/12/14a/21）共同依赖的基础设施，
> 并以产品行为验收（不是纯技术票）：

> - **结局快照（outcome snapshot）**：按 Source 落盘的**完整可回放**
>   记录。最小字段集：`source_id`、输入指纹、资产版本（占位，当前恒为
>   默认版本）、Source 实体状态、全部候选单元（含各自实体状态与理由）、
>   该 Source 贡献的可信条目、缺口条目、覆盖审计结论、提炼侧信号
>   （doubts / coverage self-check）、**完整性标记**（写毕才标记；未标记
>   的快照不得被当作有效）。
> - **canonical reader**：生产代码中的规范资产读取模块（读快照与忠实层
>   资产）。它是系统内部的重建/回放通道；后续票一律经它取回既有产出，
>   不各自手写解析。

- **产品增量**：每个 Source 一处理完即完整落盘（忠实层资产 + 结局快照，
  原子写入）；运行中途被终止后，已完成 Source 的**全部结局信息**可从
  盘上经 canonical reader 完整恢复——不依赖内存或本次运行上下文。
- **Spec 锚点**：R5.3（中间结果支持恢复）、A19（前半：中断不丢已完成
  工作）、R6.6（唯一规范数据源的读取侧——per-Source 快照自此成为可
  回放的规范事实，全局产物后续（11a）成为可由它重建的派生物）。
- **验收**：
  - 模拟第二个 Source 处理中终止 → 第一个 Source 的忠实层资产 + 快照

### 11a — 未变化且成功 Source 的跳过（含全局产物重建）

- **产品增量**：同 Corpus（同默认版本）重跑时，输入未变且上次成功的
  Source 被跳过——运行摘要以「引用既有产出」表达（不新增状态值，
  R4.6），processed / skipped 两类可辨；上次失败/待复核的 Source 不被
  跳过。全局产物（可信发布集、缺口报告、运行摘要）自此成为**可由
  per-Source 快照重建的派生物**：全跳过的重跑产出与首跑内容一致的
  全局产物。
- **Spec 锚点**：R5.4、A5、A3（处理/跳过区分；对账作用域升级为「当前
  资产版本内全量实体」——含被跳过者）、A7 第三句（失败不被误认为
  已完成）。
- **验收**：
  - 同输入两次全量运行 → 第二次全部 skipped；trusted-set 与 gap-report
    内容与首跑一致（排除 `run-metadata:` 行）；无新旧混杂；
  - 上次 `failed` 的 Source（07 场景）重跑被**重新处理**（跳过四要素
    含「上次结局为 success」）；
  - 上次 `needs_review` 的 Source（05 场景）重跑同样被**重新处理**
    （needs_review 非 success，不满足跳过四要素——增量声明「失败/
    待复核不被跳过」的两半至此均有验收）；
  - 混合场景：先成功、后注入失败的历史下，当前版本全量对账成立
    （每个 Source 与单元有下落，skipped 引用既有产出，failed 有状态）。
- **当前代码锚点**：10 票快照 + reader（判定与重建的数据源）；管线入口
  的逐 Source 判定。
- **明确不含（触界行为）**：输入变化的检测与局部重处理（11b）；显式
  资产版本（13a——版本因子当前平凡真）；已有资产目录上的范围请求
  （11b 开放）。
- **票内裁定**：Open Impl 4 四要素校验初始实现（指纹一致 + 版本一致
  〔当前平凡真〕+ 上次 success + 快照完整性标记有效）；skipped 在运行
  摘要中的表达形态。
- **依赖**：05（needs_review 状态先于跳过语义存在，硬）、10（硬）。
