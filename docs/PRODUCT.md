# Subtitle Forge — 产品定义

> 状态：**R3 收口，grilling 完成**（2026-09-01）。本文件记录已与第一用户确认的全部产品结论。2026-09-01 经独立一致性审查后修订（术语轴分离、知识单元/聚合知识定义、实体状态与缺口类别分离）。

## 产品定义（收口）

Subtitle Forge 是一个面向单人、本地运行、可分阶段执行和重算的 AI 原生批量知识提炼系统。

- V1 以**百集级、中文为主的知识型字幕和转写文本**为真实使用基准，将每个 Source 独立转换为具有可验证来源定位的分层知识资产。
- **知识生成与可信审查相互分离**；只有达到可信要求的知识单元进入可信发布集，失败、拒绝和知识覆盖缺口都必须显性保留。
- 规范知识资产按 Source 组织，同时面向人和 AI 使用；跨 Source 的关联、重复、深化、矛盾以及检索结构属于可以重新生成的衍生层。
- 产品设计不锁死语言、输入格式和未来规模。

## 定位

Subtitle Forge 是一个 AI 原生的批量知识提炼引擎：把已有文本内容（字幕、转写）可靠地转换成结构化、可信、可检索、可继续加工的知识资产。

**不是**字幕工具。ASS 是当前最主要的一类输入，但产品概念是"对已有字幕或转写文本做知识提炼"，不绑定 ASS 格式。

## "AI 原生"的含义

AI 不是附加功能，而是知识理解、提炼、审查、再组织整个认知过程的核心能力。系统从产品层面默认 AI 参与多个认知环节，而不是把 AI 当成传统流水线末尾的一次摘要 API。

Agent 驱动、自愈、调度是这种理念下的重要能力，但产品不绑定 Claude Code、cc-suite 或任何单一 agent 工具。

## V1 用户与规模

- **第一用户**：作者本人。单机个人知识提炼工具，无账号、权限、多租户。未来可扩展多人，当前不考虑。
- **语料类型**：知识口述类为主——课程、讲座、知识型视频、访谈、课堂录音经转写形成的文本。
- **语言**：当前为全中文内容；产品设计不把系统限定成只能处理中文（未来：纯英文、中英混合）。当前阶段不要求所有语言能力完整。
- **规模基准**：百集级（当前真实规模 ≤100 个 Source）为 V1 实际使用基准；在产品设计上不堵死向千集级扩展的路，但不为未来规模提前引入当前不必要的复杂度。

## 消费方式与资产要求

最终消费方式多样：人工阅读、AI / RAG 问答、二次加工、写作素材、其他知识产品。**底层知识资产不绑定任何单一消费方式。**

首要目标：形成人和 AI 都能理解、查询和继续使用的高质量知识资产。

## 质量优先级

**可信 > 信息完整性 > 结构化 > 可检索 > 可继续加工**

- **可信**：不能把原始内容中不存在的信息当作事实。
- **信息完整性**：不能为了压缩而遗漏真正重要的知识。

这两个维度必须独立看待："没有胡编"不等于"没有漏掉重要内容"。

## V1 边界（非目标）

1. **ASR 语音识别**：不做。输入应已存在文本或字幕。
2. **视频/音频下载**：不做。
3. **翻译**：不做。
4. **字幕时间轴编辑、人工字幕修复**：不做。但系统需要能够容忍常见噪声和转写错误。
5. **输入格式**：不把产品边界定义为"只接受 ASS"。首批真实数据主要是 ASS；其他格式是否首版支持，后续决定。

## 知识资产模型（R2 确认）

**分层结构，不是 Claim-first。**

- 知识资产采用分层组织：基础的知识单元（含声明）向上聚合成要点/主题，顶部有全篇概要。
- 声明（Claim）是重要的表达能力——一条可独立成立、挂来源引用的断言——但不是唯一的知识原子。课程中的方法、解释、论证过程、案例等，不应为了适配 Claim 模型而被强行碎片化。

**知识单元与聚合知识（审查修订时确认）。**

- **知识单元（Knowledge Unit）**：知识资产中可以被独立引用、审计、接受、拒绝或待复核的基础语义产物单位。不要求是 Claim，也可以是方法、解释、案例、论证、结论等具有独立知识含义的表达。
- **聚合知识（Aggregate Knowledge）**：主题摘要、整篇概要等，由一个或多个 Knowledge Unit 聚合形成。可以单独接受质量审查，但不与基础 Knowledge Unit 共用同一套单元级状态和通过率指标。
- 由此保持"分层结构、非 Claim-first"，同时避免把宏观摘要和微观知识单元混在同一审计尺度里。

**来源引用是产品级要求。**

- 原则上每个重要知识单元都应有可追溯的来源引用（Source Reference）。
- 带时间轴的字幕：原文文本片段 + 时间区间。
- 不带时间轴的转写文本：文本位置或其他定位信息。**时间戳不是产品层面的硬依赖。**

**忠实层 / 审查层分离。**

- 忠实层忠实表达来源内容；审查层产生审查注记（Review Note），如"疑似口误""与常识冲突"。
- V1 不要求系统判断外部世界中的事实真伪；也**不允许**系统因怀疑内容错误而偷偷修改忠实层内容。
- 审查注记属于系统判断，必须明确标注，与忠实层知识分离。

**基础层 / 衍生层分离。**

- 每个 Source 的提炼结果（基础层）必须能独立成立。
- 跨 Source 的重复、关联、深化、矛盾属于衍生层，可以整体重算，但不得反向污染基础层。

注：忠实层/审查层与基础层/衍生层是**两个正交的分离维度**——前者按"谁说的"（来源内容 vs 系统判断）分离，后者按 Source 作用域分离。术语定义见 `CONTEXT.md`。

## 质量保障机制（R2 确认）

V1 全部包含：

1. **忠实性审计**：检查证据确实来自原始来源（逐字引用真实存在，可程序比对）。
2. **推理审计**：检查知识表达没有超出来源支持的范围（断言能从引用推出，而非模型脑补）。
3. **生成与审计分离**：提炼与审计至少作为两个独立认知环节存在。是否使用不同模型不作为产品要求。

**信息完整性的验收含义 = 知识覆盖**（R2 确认）：

- 重要知识应充分覆盖：核心概念、方法、论点、解释、重要案例、条件和结论。
- 重复表达、寒暄、口头填充、低信息量过渡不需要逐段进入知识资产。
- **信息完整性 ≠ 文本完整性。**

## 领域概念层级（R2 确认）

- **语料集（Corpus）**：一批相关输入组成的集合，如一整套课程。批处理单位。
- **来源（Source）**：可独立处理和追溯的输入单位，如一集课程、一场访谈、一份字幕或转写。独立提炼单位。
- **片段（Segment）**：Source 内可定位的语义片段。引用锚定的目标。

完整术语见根目录 `CONTEXT.md`。

## 成功标准（R3 确认）

成功标准分两层：**运行可靠性**与**知识质量**。

1. **可信性指标必须与知识覆盖指标成对存在**——避免"少提炼、少出错"反而得到更高质量分。保守提炼在指标体系下无利可图。具体指标形式（如审计通过率）属于待校准的候选，不预先固化为唯一定义。
2. **输入-输出对账**：所有 Source 和知识单元都必须有明确下落（见"实体状态"），不允许静默消失。
3. **拒绝粒度**：可信性拒绝只发生在知识单元级；全局性错误允许中止整个批次。
4. 具体阈值（通过率、覆盖率目标）等真实 V1 运行数据出现后校准，不预先拍板。

## 实体状态与缺口类别（审查修订时确认）

**实体状态（Entity Status）按实体限定：**

- **Source 级**：成功、失败、待复核。**Source 级没有"拒绝"状态。** Source"成功"指该 Source 的处理流程完成，且其 Knowledge Unit 都有明确下落——其中可以包含已通过与已拒绝但已记录的单元。
- **Knowledge Unit 级**：通过、拒绝、待复核、失败。"拒绝"只发生在这一级。
- **待复核（Needs Review）**的严格含义：系统当前无法可靠判定该 Knowledge Unit 应通过还是拒绝，但存在足够理由需要人工或后续审查。不是"低质量"的兜底状态，也不是一般警告。
- **"低可信"不是独立状态或领域术语**，只作为触发待复核或提高抽查优先级的风险信号。

**缺口类别（Gap Category）不是实体状态：**

- 缺口报告中的四类——执行失败、审计拒绝、覆盖存疑、警告——是缺口的分类维度，不与 Source / Knowledge Unit 的实体状态共用或混用。

**对账与运行摘要（规格化时裁决）：**

- 完整的 Source / Knowledge Unit 去向对账属于**运行摘要（Run Summary）**；对账作用域为当前资产版本内的全量实体，本次运行实际处理的实体单独可辨。
- 缺口报告只记录异常与缺口，不承担全量正常对账职责。
- 成本与耗时的可观察记录是运行摘要的组成部分（物理文件是否分开是实现决策）。

**覆盖审计与 Review Note 归属（规格化时裁决）：**

- 正式的**知识覆盖审计**属于独立审查环节的职责；提炼阶段可产生覆盖自检信号，但生成者自评不作为最终覆盖结论。
- **Review Note 属于审查层产物**：提炼阶段可以发现疑点，但正式 Review Note 由审查环节确认并产出，以保持忠实层与审查层分离。

**无时间轴输入与阶段拓扑（规格审查后裁决）：**

- V1 不把无时间轴输入纳入正式验收范围；Source Reference 的概念不把时间戳作为成立必要条件（未来兼容约束，非 V1 交付能力）。
- "阶段化运行和局部重算能力"是产品要求；任何具体阶段拓扑（如 Parse/Extract/Audit/Assemble）不是产品强制架构，仅为参考管线模型。产品不变量：生成与审查认知责任分离；关键步骤可独立恢复/重算；发布集成员资格由可信审查结果决定；失败或规则变化不要求全量无条件重做。
- 实体状态只定义可观察语义（见"实体状态与缺口类别"），不定义完整状态迁移图；"跳过"是运行行为不是实体状态。

## 重算与版本语义（R3 确认，产品原则）

V1 必须满足（实现机制不锁定）：

- 能识别**输入是否发生变化**；
- 能**区分不同提炼/审计标准生成的资产版本**；
- 同一版本重跑**不会留下新旧结果混杂**；
- 已成功且未发生变化的结果**可以跳过**；
- **失败结果不应被误认为已完成**（跳过判定不能只看"产物存在"）；
- 用户**不直接修改生成资产**，规则变化通过新版本重新生成。

## 运行形态（R3 确认，产品要求）

"阶段化运行能力"，不锁定具体命令设计：

- 用户可以**一次运行完整流程**；
- 流程内部**关键阶段可以独立重跑**；
- 某阶段失败或规则改变时，**不要求整个 Corpus 从头执行**；
- 中间结果可以**支持恢复和继续执行**。

CLI 命令数量与命名属于实现决策。

## 人在环节中的位置（R3 确认）

抽查介入，**风险驱动**。人工主要查看：失败项、被拒项、低可信项、覆盖存疑项、随机抽取的已通过结果、高价值 Source。

人的反馈原则上转化为**可重复的规则或提炼标准**再重新生成，不直接手工修改生成资产。

## 缺口显性化（R3 确认）

缺口报告是**一等资产**，人和 AI 都能理解。至少区分四类（缺口类别，非实体状态）：

1. 执行失败
2. 审计拒绝
3. 覆盖存疑
4. 警告

全局性错误可以中止整批运行。

## 成本原则（R3 确认）

不设固定金额或时间承诺。原则：**质量优先，同时成本和耗时必须可观察、可比较、可控制**。

系统不得为了节省成本而静默降低可信要求——任何进入可信发布集的知识都必须满足既定可信标准。全量 / 分层 / 风险驱动审计的选择属于后续经真实数据验证的实现决策。

## 资产形态要求（R3 确认）

1. **规范知识资产必须是可移植、可独立保存的文件资产**；
2. 运行时可以存在**可删除、可重新生成的索引与缓存**；
3. **人和机器都是一级消费者**；
4. 基础知识资产与 **Source 保持明确对应**；
5. 跨 Source 关系与检索结构属于**可重建的衍生层**；
6. 必须存在**唯一规范数据源**，避免多个表示之间发生双向漂移。

哪种文件格式作为规范源属于后续实现决策。
